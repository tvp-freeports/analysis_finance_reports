# The formats repository

A formats repository is an ordinary directory, tracked in its own version control, holding the
recipes for a set of report layouts. The engine reads it; it is not part of the engine.

That separation is the project's main structural bet. Support for a new report needs no release of
the engine, touches nothing anyone else maintains, and can be published by whoever cares about those
reports. `analysis_finance_reports_formats` — *Italy, five top groups* — is one such repository, and
there is nothing privileged about it.

## Starting a repository
```console
$ freeports-dev init-format-repo path/to/my-formats
$ cd path/to/my-formats
$ freeports-dev setup-input-db          # a minimal input database, for the tests
```

## The layout of a repository
```text
package.yaml                     identity and version of the repository
metadata/
  formats.csv                    the formats it supports
  url_mapping.csv                which URLs belong to which format
content/
  orchestration/
    algorithms_schedule.csv      the order pages are processed in, split into steps
    mapping.csv                  which pipelines handle which page class
    pageclassify_overwrite.csv   formats that classify pages their own way
  algorithms/
    structured/                  CSV parameters for library algorithms
    semistructured/              named algorithms plus YAML configuration
    unstructured/                Python, one module per format
  templates/                     shared fragments a format can build on
tests/
  formats/<FORMAT>/report.pdf    the document
  formats/<FORMAT>/pages/…       per-page fixtures
  formats/<FORMAT>/out/…         the expected output tables
  input_db/                      the companies the tests look for
validation/                      who vouches for what, and under which methodology
```

## The `metadata/` tables
`metadata/formats.csv` lists the formats by their **components**, not by their names:

```text
Name,Locale,Year,Country,Version
AMUNDI,EN,24,,
ANIMA,EN,23,,
```

The name every other file refers to — `AMUNDI-EN24` — is **synthesised** as
`Name-Locale<YY>[@Country][.Version]` and written nowhere. There is exactly one place a format name
comes from, so a name and its components cannot disagree.

`metadata/url_mapping.csv` maps URL prefixes to format names, and is what lets a document downloaded
from a known address be read without `--format`. The **order matters**: the first matching prefix
wins.

## Orchestration

Three tables decide what runs and in what order; {doc}`../design/schedule` explains why they have this
shape.

**`algorithms_schedule.csv`** — per format, the page classes in processing order, split into steps.
Classes accumulate into the current step until a row raises `Filter next iteration`, which closes it
and opens the next. That flag is how you say "the results so far are the filter for what comes
next":

```text
Format name,Page type,Filter next iteration
ANIMA_SGR-IT24,investments,TRUE
ANIMA_SGR-IT24,merges,
ANIMA_SGR-IT24,sfdr_classification,
```

Here `investments` runs first and alone; the two remaining classes run in a second step and can
filter on what the first found.

**`mapping.csv`** — which pipelines handle which page class, keyed by `{format}({pipeline})`. Left
unspecified, a page class is handled by the pipeline of the same name. Several rows may point at one
class, and one pipeline may serve several classes.

**`pageclassify_overwrite.csv`** — the formats that replace the standard page classification with
their own pipelines. Empty in the common case.

## Tests, and what they are for

Each format under `tests/formats/<FORMAT>/` has the report, per-page fixtures, and the expected
output.

The per-page fixtures — `<page>-pdf_blks.json`, `<page>-txt_blks.json`, `<page>-results.json`, plus
a `filter_data.json` per page class — pin one page at a time and are generated by
`freeports-dev make-tests`. They are what tells you which segment broke.

`out/` is different in kind. It is the **expected output of the whole document**, and it is the
repository's specification: if a run diverges from it, the engine is what changed, not the
expectation. Regenerating one of those files is a deliberate act with a reason attached, never a way
to make a red test go green. That is also what makes the grants in {doc}`../validation` meaningful —
a grant is a claim about the content of exactly these files.

Run them with `freeports-dev test`, optionally narrowed with `--format`. {doc}`dev-loop` is the
workflow, {doc}`tooling` the option-by-option reference.

## Versioning and identity

`package.yaml` carries the repository's own identity:

```yaml
schema: v0.0.0
info:
  description: "Italy - 5 top groups"
  version: v0.0.0
  validation_sha256: 4dfe67c2…
```

`validation_sha256` ties the repository to the validation document that vouches for its contents, so
that a consumer can tell not only *what* they have but *what was claimed about it*.
